# Архитектура беты

Браузер → Nginx → Spring Boot → PostgreSQL (метаданные) + файловое хранилище (шифротекст). В разработке роль proxy выполняет Vite. Один backend держит PostgreSQL advisory lock на выделенном соединении; второй экземпляр не запускается. Реплики и балансировка нескольких backend не поддерживаются. Потеря выделенного соединения снимает готовность backend; для повторного получения блокировки нужен перезапуск.

## Передача и секреты

Создание: `POST /api/transfers`, multipart с JSON-частью `options` и необязательной частью `file`. Пример options: `{"kind":"TEXT","text":"Привет","ttlSeconds":600,"maxDownloads":1}`; для файла kind=FILE. Необязательный `password` — до 128 символов. API принимает TTL 600–604800 секунд и лимит 1–10; интерфейс предлагает фиксированные значения.

Ответ 201: `readToken`, `manageToken`, `transfer`. Оба токена — 32 случайных байта в base64url (43 символа), база хранит SHA-256. Ссылки `/s/{readToken}` и `/manage/{manageToken}` независимы. GET метаданных не открывает содержимое; у защищённой передачи публичное имя скрыто до получения. Сами ссылки — секреты. Nginx не пишет пути запросов в access/error log; клиент не использует внешние шрифты, аналитику или рекламные скрипты. Метаданные и управление возвращаются с `Cache-Control: no-store`.

- `GET /api/health` — готовность и версия.
- `GET /api/transfers/{token}` — публичные условия и состояние.
- `POST /api/transfers/{token}/download` — JSON `{"password":"..."}` либо `{}`; явная выдача бинарного файла или UTF-8 текста.
- `GET /api/manage/{token}` — состояние для отправителя.
- `DELETE /api/manage/{token}` — отзыв, 204.

Ошибки: 400 неверные параметры, 401 пароль, 404 неизвестная ссылка, 409 выдача уже идёт, 410 доступ закончился, 413 размер, 429 попытки пароля, 507 квота хранения. API не разрешает CORS: браузер работает с тем же origin.

## Выдача и обрыв

Транзакция блокирует строку передачи (`SELECT … FOR UPDATE`), проверяет срок/лимит/отзыв/пароль и записывает уникальный резерв. Ответ выдаётся вне этой транзакции; целостность AES-GCM проверяется до первого байта. Перед каждым блоком 64 КиБ повторно проверяются срок, отзыв и принадлежность резерва. В отдельной транзакции резерв снимается, счётчик увеличивается только после полной отправки и flush. IOException освобождает резерв без расходования лимита. Идентификатор резерва не позволяет старому потоку завершить новую выдачу.

Повтор разрешён после обнаруженного сервером обрыва. Успешная серверная отправка не означает сохранение пользователем; принятый получателем фрагмент нельзя отозвать. Получение целиком в браузере использует Blob, а сервер проверяет GCM в памяти; каждый файл ограничен 25 МиБ, многопользовательская нагрузка ещё не проверялась.

При запуске единственный backend сбрасывает оставшиеся резервы, удаляет сиротские файлы и запускает очистку. Очистка каждые 30 секунд удаляет истёкшие, отозванные и исчерпанные файлы, если выдача не выполняется. Метаданные остаются для экрана управления. Сбой удаления повторяется в следующем проходе. Журнал содержит тип события и внутренний UUID, без паролей, токенов, имён и содержимого.

## Хранение

Формат файла: байт версии 1 + случайный 12-байтовый nonce + AES-256-GCM шифротекст и тег. UUID включён как AAD. Запись через временный файл с атомарным перемещением. Ошибка транзакции создания удаляет связанный файл. Argon2id: память 64 МиБ, 3 итерации, параллелизм 1, соль 16 байт. Пять неверных паролей на сочетание передачи и адреса прямого подключения блокируют дальнейшие проверки на 15 минут, в памяти процесса.

Ключ хранится отдельно в `.env`. HTTPS на внешнем proxy обязателен для публичного использования. Ротация ключа, антивирус, масштабирование, резервное копирование и автоматическая политика удаления метаданных — дальнейшие задачи, не возможности этого выпуска.
